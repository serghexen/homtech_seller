# Инструкции по разработке HomTech Seller

Перед изменением бизнес-логики прочитайте `docs/ARCHITECTURE.md`. Для выдачи,
пулов, Supplier Hub и переноса из CRM также прочитайте
`docs/FULFILLMENT_MIGRATION_PLAN.md`. Для Ozon используйте
`docs/OZON_CRM_CUTOVER_CHECKLIST.md`.

## Seller всегда проектируется как multi-tenant SaaS

- Любые бизнес-данные принадлежат `workspace`; магазин определяется конкретным
  `connection_id`. Нельзя доверять `workspace_id` из пользовательского запроса:
  workspace получают из аутентифицированного контекста и проверяют членство.
- Запросы к данным карточек, заказов, ключей, настроек и заданий должны быть
  ограничены workspace и подключением. Нельзя находить запись только по внешнему
  номеру заказа, SKU, offer ID или названию магазина.
- У каждого подключения собственные зашифрованные credentials, расписание,
  rate-limit/backoff, ошибки и kill switches. Состояние одного магазина не должно
  изменять или блокировать другой магазин.

## Очереди и worker-ы

- Не создавайте отдельный in-memory опросчик на пользователя или магазин.
  Расписание хранится в PostgreSQL, а stateless worker-ы забирают задания из общей
  долговечной очереди.
- Каждое задание несёт как минимум `workspace_id`, `connection_id`, тип операции и
  идемпотентный бизнес-ключ. Одно подключение нельзя одновременно обрабатывать
  несколькими worker-ами: используйте уникальное активное задание, `SKIP LOCKED`
  и advisory lock по `connection_id`.
- Очередь должна безопасно масштабироваться несколькими одинаковыми worker-ами.
  Добавление реплик не должно создавать повторную выдачу, повторную покупку у
  поставщика или пересечение магазинов.
- Планировщик распределяет периодические задания во времени (stable jitter), а
  выдача должна быть справедливой между workspace/подключениями. Медленный или
  сломанный магазин не должен занять всю очередь.
- Временные `429`, сетевые ошибки и `5xx` получают ограниченный backoff. Для
  неидемпотентного внешнего действия неопределённый сетевой исход переводится в
  `unknown` и запрещает слепой повтор.
- Перед сетевым вызовом состояние внешней операции фиксируется транзакционно.
  Повтор доставки события или перезапуск worker-а не должен повторять результат.

## Новые возможности и миграции

- Настройки, тарифы и разрешения, которые нужно менять без рестарта, хранятся в
  БД. Опасные внешние действия дополнительно закрываются глобальным, магазинным и,
  где нужно, товарным kill switch; значения по умолчанию выключены.
- Миграция не должна незаметно менять существующее рабочее поведение. Источник CRM
  открывается только для чтения, перенос по умолчанию выполняется как dry-run,
  открытые ключи не пишутся в файлы и логи.
- Магазины переключаются по одному. CRM и Seller никогда одновременно не владеют
  выдачей одного магазина. При состоянии `sending`, `unknown` или другой
  незавершённой внешней операции переключение блокируется.
- Для новой очереди или фоновой возможности заранее оцените работу минимум для
  20 и 100 магазинов: число внешних запросов, среднее/худшее время задания,
  необходимое число worker-ов, лимиты API и поведение при массовом восстановлении.
- Обязательные тесты: изоляция двух workspace, конкурентный захват задания двумя
  worker-ами, повтор одного события/задания, падение после фиксации состояния и
  недоступность одного магазина без задержки остальных.

## Наблюдаемость

Для каждой фоновой интеграции сохраняйте и показывайте отдельно по подключению:
время последнего успеха, последнюю ошибку, время следующего запуска и задержку
очереди. На уровне сервиса нужны метрики глубины/возраста очереди, длительности
заданий, повторов, `429`, `unknown` и dead-letter состояний.
