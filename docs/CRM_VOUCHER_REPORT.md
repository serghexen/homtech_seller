# Отчёт о ваучерах в CRM

В CRM → Платежи → Interhub владелец нажимает «Отчёт», задаёт две даты и скачивает XLSX.
Даты включительны, зона Europe/Moscow; продажа датируется подтверждённой выдачей.
Сегодняшний день ограничивается моментом запроса. Максимум 366 дней и 20 000 строк.
Пустые магазины не получают лист. На каждом листе название магазина, затем таблица:
номер заказа, сервис, номинал, закупочная цена в рублях, дата продажи, комментарий.

## Подключение

На Seller задать `SELLER_CRM_REPORT_TOKEN` (отдельный случайный секрет минимум 32 символа)
и `SELLER_CRM_REPORT_USER_ID` (ID действующего владельца нужной организации).
На CRM задать такой же `SELLER_CRM_REPORT_TOKEN` и `SELLER_REPORT_URL` — HTTPS адрес Seller API,
например `https://seller.homtech.app/api`. Допускается origin без пути или префикс `/api`. Для локальных тестов разрешён HTTP localhost.
Секрет не использовать повторно для Hub, пользовательских сессий или других интеграций.
Без этих настроек отчёт закрыт. Миграции для этой возможности не нужны.

CRM вызывает `GET /internal/reports/voucher-sales` с заголовком `X-Voucher-Report-Token`.
Seller получает workspace из проверенного членства серверного пользователя, а не из запроса.
Этот мост предназначен для одной доверенной CRM одного владельца: нельзя подключать его
к общей CRM разных организаций. Отозванное членство прекращает доступ.
CRM требует своё существующее право owner для выгрузки.

## Сверка

Выгружаются выдачи Seller с источниками supplier, manual и pool. Служебные сообщения исключены.
Автоматическая цена берётся из успешной покупки Interhub, связанной с выданным ключом.
CRM сверяет ручные выдачи и пул с оплаченными локальными закупками Interhub и историческими
AirPay по SHA256 кода. Открытые коды Seller не передаёт, CRM не записывает их в файл или логи.
Совпадения только по времени или номиналу не подтверждают стоимость.
Комплект требует полного однозначного покрытия всех кодов; одна покупка не учитывается дважды.
Неполная, неоднозначная или отсутствующая цена отмечается «Не подтверждена», без подстановки нуля.
Ручные выдачи выделены жёлтым, пул — сиреневым, неподтверждённые — красным.
Подробности закупок остаются в комментарии к ячейке. Верхних подписей периода, счётчиков и легенды нет.

В этом контракте нет удалённого архива AirPay Hub и продаж, выданных только старой CRM до Seller.
Для таких периодов требуется отдельный источник; текущая выгрузка охватывает подтверждённые выдачи Seller.

## Нагрузка и проверка

Отчёт формируется только по запросу, без расписаний и worker-ов. CRM удерживает общую
транзакционную advisory-блокировку; второй запрос получает 409 и может быть повторён.
Оба источника читаются в read-only транзакциях. Сбой источника отменяет весь файл.
При 20 и 100 магазинах число сетевых вызовов одинаковое: один запрос CRM → Seller,
без запросов к API магазинов и поставщика. Seller выполняет одну выборку продаж и одну
пакетную расшифровку ручных ключей/ключей пула; CRM — две выборки каталога и один проход архива покупок
плюс поиск в локальном AirPay. Ограничения: 20 000 строк, 500 000 проверенных закупок,
45 секунд на SQL, 60 секунд HTTP, 20 MiB ответа. Для больших периодов следует уменьшить диапазон;
перед расширением лимитов нужна долговечная очередь и измерение нагрузки на реальных объёмах.

Автотесты: `api/tests/test_voucher_report_unittest.py` в Seller;
`api/tests/test_voucher_sales_report_unittest.py` и `WorkVoucherReport.vitest.test.js` в CRM.
Перед включением проверить владельца/организацию, затем скачать небольшой прошлый диапазон
и сверить суммы. Ручную проверку модального окна WorkView выполняет пользователь согласно CRM AGENTS.md.
Production подключается и выкладывается только по отдельному запросу; изменения сначала коммитятся и пушатся.
