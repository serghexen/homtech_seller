# Архитектура HomTech Seller

## Назначение

HomTech Seller — отдельный SaaS-кабинет для продавцов цифровых товаров. На первом этапе он только читает данные Ozon и Яндекс Маркета и хранит собственный снимок подключений, каталога, остатков и заказов.

## Изоляция от CRM

Seller и CRM не используют общую PostgreSQL-базу, общие Docker volumes или доступ к таблицам друг друга. Связь между ними в будущем строится через публичный контракт идентификации:

```text
Пользователь → Identity/SSO → Seller API → Seller PostgreSQL
                         └──→ CRM API → CRM PostgreSQL
```

`auth_subject` в `seller.users` — внешний стабильный идентификатор пользователя. До SSO Seller использует собственные email/пароль-аккаунты и безопасный HttpOnly cookie. После подключения SSO поле станет идентификатором общего Identity Provider. Прямые межбазовые foreign key запрещены.

## Мультиарендность

`workspace` — организация клиента. Все бизнес-данные привязаны к ней через подключение магазина:

```text
workspace → marketplace_connection → catalog_item / order_item
```

Участник организации имеет роль `owner`, `operator` или `viewer`. Каждая API-операция в будущих маршрутах должна получать организацию из аутентифицированного контекста и проверять членство, а не принимать произвольный `workspace_id` от клиента.

## Секреты

- `MARKETPLACE_CREDENTIALS_SECRET` — отдельный для Seller ключ шифрования токенов;
- ключ не коммитится, не попадает в логи и не совпадает с CRM-ключом;
- старые CRM-токены не копируются: пользователь подключает магазин повторно;
- поле `encryption_key_version` позволит провести управляемую ротацию ключа.

## Развёртывание

На новой VM запускается один Docker Compose stack:

```text
reverse proxy (TLS)
  ├─ web
  └─ api              # localhost:18080

api ─────┐
worker ──┴─ postgres  # очередь и снимки, только внутренняя Docker-сеть
  └──────── Ozon / Яндекс Маркет (только read-only запросы)
```

Перед запуском API миграции выполняются отдельным одноразовым контейнером `migrate`. Резервные копии PostgreSQL отправляются вне VM; восстановление проверяется регулярно.

## Контракт первого релиза

Разрешено: проверять токен, получать список магазинов, синхронизировать и показывать каталог, актуальные остатки и заказы.

Запрещено до отдельного проектирования: выдавать ключи, подтверждать доставку, отправлять чат-сообщения, менять остатки, цены и статусы заказов в Ozon или Яндекс Маркете. Единственное явное изменение карточки — подтверждённый пользователем перенос товара Яндекс Маркета в архив или восстановление из него.

## Синхронизация заказов

HTTP API создаёт задания `queued` в `seller.marketplace_sync_jobs` и сразу возвращает управление интерфейсу. Отдельный worker переводит их в `running`, а затем в `succeeded` или `failed`. PostgreSQL advisory lock не допускает одновременную работу с одним подключением; временные сетевые ошибки, `429` и `5xx` повторяются с exponential backoff. Задание после аварийного завершения worker-а возвращается в очередь.

Интерфейс не блокируется на время задания: компактный индикатор показывает ход фонового обновления во всех разделах. После перезагрузки страницы незавершённые задания восстанавливаются по `/marketplaces/sync-jobs`, а после завершения локальные снимки перечитываются автоматически.

Исключение — интерактивная проверка остатка одной открытой карточки Яндекс Маркета. API выполняет один ограниченный read-only POST, обновляет только локальный снимок и возвращает время проверки; методов публикации остатка в Seller нет.

Редактируемые параметры карточки хранятся отдельно в `seller.product_card_settings`. Они перекрывают импортированный снимок CRM для отображения в Seller, поэтому повторный импорт не затирает локальные изменения. Сохраняются заданный остаток, дневной лимит, дополнительный лимит на текущий день, инструкция покупателю, разрешение пула и шаблон выдачи через поддержку. Endpoint сохранения не читает токен подключения и не вызывает API маркетплейса; публикации этих значений пока нет. Интерфейс показывает фиксированный безопасный приоритет `Supplier Hub → пул → поддержка → ручной ввод`, но до реализации Supplier Hub и resolver-а это только конфигурация карточки под общими выключенными kill switch.

Ручные коды хранятся отдельно в `seller.marketplace_key_pools` и `seller.marketplace_keys`. Один пул принадлежит одной карточке конкретного подключения. Значение кода шифруется отдельным `SELLER_KEY_POOL_SECRET`, а список возвращает только маску и состояние. В карточке заказа оператор может выбрать полный комплект из пула или однократно ввести ровное заказу число кодов. Ручной комплект шифруется и сразу закрепляется за выдачей; открытые значения в ответ API не возвращаются.

Локальная модель выдачи хранится в `seller.order_fulfillments`: одна идемпотентная запись соответствует одной цифровой позиции DBS-заказа Яндекс Маркета (`delivery_type=DIGITAL`). Физические позиции исключены на уровне сервиса, API и интерфейса; ранее ошибочно созданный обратимый резерв закрывается и освобождается. Связь с зарезервированными ключами и история переходов вынесены в отдельные таблицы. Полный комплект резервируется одной транзакцией через `FOR UPDATE SKIP LOCKED`; до резерва значения ключей не читаются и не расшифровываются, а частичный комплект запрещён. Отмена заказа освобождает только ключи в локальном состоянии `reserved`; состояния будущей отправки автоматически не откатываются.

Автоматический резерв требует одновременно трёх разрешений, каждое по умолчанию выключено: `SELLER_POOL_RESERVATION_ENABLED=true`, `fulfillment_reservation_enabled=true` у подключения и `pool_issue_enabled=true` у товара. Поэтому применение миграции и обработка webhook сами по себе не начинают выдачу.

Явная ручная подготовка доступна только `owner` и `operator` для активного цифрового DBS-заказа Яндекс Маркета в состоянии `processing`. Источником может быть пул, ручной комплект или неизменяемый снимок заранее сохранённого для товара сообщения поддержки. Подготовка обходит только auto-флаги и не вызывает Яндекс. Отдельное действие снимает локальный `reserved`-комплект; состояния `sending`, `submitted`, `unknown` и `delivered` таким способом не откатываются.

Над ручными действиями находится независимый kill switch `SELLER_MANUAL_FULFILLMENT_ENABLED`, по умолчанию `false`. Выключатель проверяется до открытия соединения с БД, поэтому прямой HTTP-запрос также не может обойти режим просмотра. Его включение не включает webhook, автоматический резерв или outbound.

Внешняя отправка цифрового комплекта Яндекс Маркету вынесена в `seller.fulfillment_outbound_jobs`. API не расшифровывает коды и только создаёт `queued`-задание после отдельного подтверждения владельца или оператора. Worker повторно проверяет активность магазина, цифровой тип заказа, статус `processing`, точное число зарезервированных ключей и заполненную инструкцию; затем расшифровывает токен и коды только в памяти процесса. Отправка требует одновременно `SELLER_YANDEX_OUTBOUND_ENABLED=true` и `fulfillment_outbound_enabled=true` у магазина.

Перед HTTP-запросом worker транзакционно фиксирует `sending`. Успешный ответ создаёт `submitted`, но ключи становятся `delivered` только после подтверждения состояния заказа Яндексом через webhook или polling. Однозначный отказ `4xx` оставляет полный комплект в локальном резерве. Таймаут, сетевой сбой, `5xx` или падение worker-а после `sending` переводят задание и выдачу в `unknown`: автоматического повтора из этой точки нет. Брошенный `preparing`, напротив, безопасно возвращается в очередь, поскольку сеть ещё не вызывалась.

Целевой план переноса выдачи и Supplier Hub описан в `docs/FULFILLMENT_MIGRATION_PLAN.md`.

Каталог обновляется как полный снимок подключения. Seller разделяет два разных состояния: `is_present` показывает, существует ли карточка в полном ответе маркетплейса, а `is_archived` повторяет штатный архив Яндекс Маркета. Активные и архивные предложения загружаются отдельно, но хранятся вместе без удаления связанных настроек, ключей и истории. Остатки запрашиваются только для активных карточек. Архивирование и восстановление доступны отдельным endpoint только владельцу и оператору, выполняются без удержания транзакции БД во время внешнего запроса и подтверждаются следующей синхронизацией.

Первый успешный запуск заказов загружает историю за 30 дней. После него подключение хранит `last_successful_sync_at`; значение продвигается только после полной загрузки и сохранения снимка. Яндекс Маркет на следующих запусках читается по времени обновления заказа, а Ozon — со скользящим 30-дневным окном. Если сервис простаивал дольше, пропущенный период разбивается на 30-дневные интервалы.

## Inbox уведомлений Яндекс Маркета

Seller заранее публикует оба совместимых пути `/api/marketplaces/yandex/notifications` и `/api/marketplaces/yandex/notifications/notification`. Endpoint не использует пользовательскую сессию: источник проверяется по официальным подсетям Яндекс Маркета, а `X-Forwarded-For` учитывается только через доверенную цепочку reverse proxy. Nginx сохраняет цепочку адресов до API.

Уведомление сначала сохраняется в `seller.yandex_webhook_events`. Полный JSON-хеш имеет уникальный индекс; повторная доставка увеличивает `duplicate_count`, но не создаёт вторую бизнес-операцию. `PING` фиксируется как `ignored` и получает требуемый ответ с исходным временем. До контролируемого переключения с CRM `YANDEX_MARKET_WEBHOOK_PROCESSING_ENABLED=false`, поэтому события заказов получают состояние `paused`.

Для запуска нужны два независимых разрешения: глобальная переменная окружения и `webhook_processing_enabled=true` у конкретного активного подключения. Флаг магазина проверяется и при приёме, и повторно при аренде события: уже поставленная в очередь запись не обработается после отключения магазина. При включённой обработке worker забирает только `received`/`failed` либо брошенное `processing`-событие с истёкшим lease. По `connection_id` расшифровывается токен нужного активного магазина, затем через `orderIds` читается ровно один заказ и сохраняется общим методом снимков. Webhook не продвигает `last_successful_sync_at`. Периодическая синхронизация остаётся независимой страховкой и после сохранения снимков запускает ту же сверку fulfillment, включая освобождение обратимого резерва отменённого заказа. Ошибка получает exponential backoff, последняя попытка переводит событие в `dead`.

После сохранения снимка processor создаёт локальную fulfillment-запись. При выключенном третьем kill switch ключи не затрагиваются. Даже при его включении автоматический резерв дополнительно требует разрешений магазина и товара. Отправка не запускается webhook-ом напрямую: она проходит отдельную очередь и собственные выключатели. Обращения к поставщику в этом контуре нет.
