# Архитектура HomTech Seller

## Назначение

HomTech Seller — отдельный SaaS-кабинет для продавцов цифровых товаров. На первом этапе он только читает данные Ozon и Яндекс Маркета и хранит собственный снимок подключений, каталога, остатков и заказов.

## Изоляция от CRM

Seller и CRM не используют общую PostgreSQL-базу, общие Docker volumes или доступ к таблицам друг друга. Связь между ними в будущем строится через публичный контракт идентификации:

```text
Пользователь → Identity/SSO → Seller API → Seller PostgreSQL
                         └──→ CRM API → CRM PostgreSQL
```

`auth_subject` в `seller.users` — внешний стабильный идентификатор пользователя. До SSO Seller использует собственные email/пароль-аккаунты и безопасный HttpOnly cookie. После подключения SSO поле станет идентификатором общего Identity Provider. Прямые межбазовые foreign key запрещены.

## Мультиарендность

`workspace` — организация клиента. Все бизнес-данные привязаны к ней через подключение магазина:

```text
workspace → marketplace_connection → catalog_item / order_item
```

Участник организации имеет роль `owner`, `operator` или `viewer`. Каждая API-операция в будущих маршрутах должна получать организацию из аутентифицированного контекста и проверять членство, а не принимать произвольный `workspace_id` от клиента.

## Секреты

- `MARKETPLACE_CREDENTIALS_SECRET` — отдельный для Seller ключ шифрования токенов;
- ключ не коммитится, не попадает в логи и не совпадает с CRM-ключом;
- старые CRM-токены не копируются: пользователь подключает магазин повторно;
- поле `encryption_key_version` позволит провести управляемую ротацию ключа.

## Развёртывание

На новой VM запускается один Docker Compose stack:

```text
reverse proxy (TLS)
  ├─ web
  └─ api              # localhost:18080

api ─────┐
worker ──┴─ postgres  # очередь и снимки, только внутренняя Docker-сеть
  └──────── Ozon / Яндекс Маркет (только read-only запросы)
```

Перед запуском API миграции выполняются отдельным одноразовым контейнером `migrate`. Резервные копии PostgreSQL отправляются вне VM; восстановление проверяется регулярно.

## Контракт первого релиза

Разрешено: проверять токен, получать список магазинов, синхронизировать и показывать каталог, актуальные остатки и заказы.

Запрещено до отдельного проектирования: выдавать ключи, подтверждать доставку, отправлять чат-сообщения, менять остатки/цены/статусы в Ozon или Яндекс Маркете.

## Синхронизация заказов

HTTP API создаёт задания `queued` в `seller.marketplace_sync_jobs` и сразу возвращает управление интерфейсу. Отдельный worker переводит их в `running`, а затем в `succeeded` или `failed`. PostgreSQL advisory lock не допускает одновременную работу с одним подключением; временные сетевые ошибки, `429` и `5xx` повторяются с exponential backoff. Задание после аварийного завершения worker-а возвращается в очередь.

Исключение — интерактивная проверка остатка одной открытой карточки Яндекс Маркета. API выполняет один ограниченный read-only POST, обновляет только локальный снимок и возвращает время проверки; методов публикации остатка в Seller нет.

Первый успешный запуск заказов загружает историю за 30 дней. После него подключение хранит `last_successful_sync_at`; значение продвигается только после полной загрузки и сохранения снимка. Яндекс Маркет на следующих запусках читается по времени обновления заказа, а Ozon — со скользящим 30-дневным окном. Если сервис простаивал дольше, пропущенный период разбивается на 30-дневные интервалы.
