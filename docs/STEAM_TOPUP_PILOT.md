# Steam: ручной пилот одноразовых ссылок

Подготовлено 06.10.2026. Код выложен 07.10.2026 с выключенным пилотом; в 08:48 МСК по запросу владельца включён только workspace 3 с общим бюджетом 100 ₽ и выпущена одна ссылка. Финальное нажатие передано владельцу. Итог, проверки и откат: [STEAM_TOPUP_RELEASE_20261007.md](STEAM_TOPUP_RELEASE_20261007.md).

## Границы

- Seller владеет ссылкой, фиксированной суммой RUB, логином, попытками и аудитом.
- Hub владеет `check → pay → check_status` InterHub, service_id=9361, kind=steam_topup.
- `homtech_info` показывает форму на market.homtech.app и существующую поддержку.
- CRM, marketplace fulfillment, пулы, остатки, статусы и сообщения магазинов не участвуют.

Для согласованного пилота источник — `manual_pilot`; workspace обязателен,
`connection_id` явно NULL. Подключать фиктивный магазин нельзя. Это отдельный
сценарий, а не ослабление tenant-проверок marketplace. При подключении реальных
заказов потребуется новая миграция: обязательный connection_id, точная позиция
заказа, единица товара, eligibility и отмена в одной транзакции.

Сумма — аргумент amount в check, как в проверенном рабочем TOP_UP-сценарии CRM.
Для этой услуги calculate номинала не вызывается. Это сумма к отправке поставщику,
не гарантия точной суммы в валюте кошелька. Фактическую конвертацию и комиссию
нужно сверить при первом личном пополнении. Не использовать слова «ровно 100 ₽
в кошелёк» до проверки контракта.

## Одноразовость

Владелец workspace создаёт ссылку из «Steam · пилот». Сервер принимает сумму
только здесь, проверяет отдельное разрешение, максимальную сумму и общий бюджет
пилота. Бюджет резервируется при создании ссылки; успех, ошибка или истечение
не освобождают его автоматически. Отмена ещё не начатой ссылки освобождает резерв.
Создание повторяется с одним creation_key; другая сумма под ним отклоняется.

Секретный token — UUID плюс HMAC-SHA256 от отдельного секрета. В таблице хранится
его SHA256, в URL — только fragment `#topup=…`, не передаваемый серверу или через
Referer. Фронтенд отправляет token в JSON, без cookies. Публичный API не принимает
workspace, connection_id, сумму, service_id или credentials.

`submit` блокирует запись ссылки FOR UPDATE и в одной транзакции создаёт попытку
и queued-состояние. Частичный уникальный индекс разрешает только одну активную
попытку на ссылку. Второе нажатие с тем же или другим request_key получает
состояние уже существующей попытки. Старый request_key после отказа также не
может создать новую попытку. Лимит — 10 попыток проверки, минимум 5 секунд между ними.

Seller передаёт Hub стабильный ключ `steam:workspace:link:attempt`. Потеря ответа
и повтор worker не меняют ключ, логин или сумму. Hub включает эти реквизиты и
workspace в fingerprint. Перед pay Hub фиксирует payment_started транзакционно.
После этой точки разрешён только check_status, включая падение до фактического
вызова pay. Это консервативная защита: неизвестный исход может потребовать ручной
сверки, но не разрешает слепой повтор платежа.

Успех TOP_UP не требует ваучера. Неизвестная форма ответа не считается успехом.
При failed до pay ссылка вновь допускает ввод логина; после pay или при
requires_attention её нельзя переиспользовать. После succeeded повторное
нажатие/открытие показывает итог. В Hub оператор может подтвердить проверенный
успех TOP_UP без фиктивного кода через существующий операторский resolve API.

## Worker и наблюдаемость

Отдельный общий `steam-topup-worker` запускается compose-профилем `steam-pilot`.
Долговечные попытки содержат workspace_id, connection_id=NULL, operation_kind,
idempotency-идентичность и расписание. FOR UPDATE SKIP LOCKED, lease и session
advisory lock workspace сериализуют работу реплик; приоритет по last_worker_at
даёт справедливость между workspace. Нет in-memory таймеров для отдельных клиентов.

Одна итерация делает один HTTP-вызов Hub с текущим timeout клиента (обычно 10 с).
Статус читается каждые 15 секунд только для незавершённых попыток. Сбои связи
получают backoff 15–300 с, после 20 ошибок — dead/attention. Кнопка «Сверить
прежнюю операцию» возвращает тот же ключ, а не создаёт новый платёж. Если Hub
требует операторского решения, Seller продолжает читать только его статус.

Hub повторяет безопасный check при временном ProviderError максимум 5 раз,
с паузой 30 секунд. После начала оплаты pay никогда не повторяется; действуют
существующий лимит check_status и операторская сверка. Прямой бизнес-отказ check
сохраняется как failed до оплаты. Публичный текст ошибки не раскрывает сырой ответ.

В попытках сохраняются последний успешный контакт с Hub, ошибка, следующий запуск,
lease, число повторов и длительность последнего задания. GET /steam-topups
ограничен workspace владельца и возвращает глубину/возраст очереди, время следующего
запуска, число требующих сверки операций, повторы и длительность; история в кабинете
показывает состояния ссылок. Аудит не содержит bearer-токенов и credentials.

## Ёмкость для 20 и 100 магазинов

До подключения магазинов используем эквивалентную модель: по одной активации в
минуту на workspace. Успех — 2 запроса к InterHub (check/pay), плюс check_status
при асинхронном результате. Это минимум 40/200 запросов в минуту для 20/100.
При условном среднем времени одного запроса 1 с: 40/200 worker-секунд в минуту,
минимум 1/4 Hub worker; с запасом разумно проверять 2/5. Это расчётная модель,
а не измеренные задержки или подтверждённый лимит InterHub.

При двух таймаутах по 20 с верхняя оценка одной пары — 40 с; первая волна 20/100
активаций занимает до 800/4000 worker-секунд. Для минуты это 14/67 worker только
по времени ожидания — так масштабировать без подтверждения лимитов нельзя.
При недоступности действуют backoff, лимиты попыток и очередь, а не SLA одной минуты.
Seller в норме делает 1 запрос постановки и N чтений Hub, не опрашивая поставщика
на каждый просмотр страницы. Его минимальную ёмкость следует измерить отдельно.
После массового восстановления сохраняются прежние операции и сроки; queued
не создаются заново, неизвестные платежи только сверяются. Пилот ограничен бюджетом
и одним workspace; включение 20/100 требует замеров 429 и лимитов поставщика,
раздельных credentials/rate limits и обязательного store-scoped контракта.

## Развёртывание для личного теста

1. Сначала проверить конкретные ревизии всех трёх проектов и резервные копии.
2. Применить миграцию Hub 20261006_01_steam_topups.sql, обновить его API и все
   worker-реплики при INTERHUB_TOPUPS_ENABLED=false. Старые worker не должны
   обрабатывать новый тип. Ваучерные fingerprint сохранены.
3. Применить Seller 20261006_01_steam_topup_pilot.sql, обновить API/web и добавить
   отдельный случайный SELLER_STEAM_LINK_SECRET. SELLER_STEAM_TOPUPS_ENABLED=false.
4. Обновить homtech_info через Docker Compose. Его Caddy передаёт только POST
   /topup-api/status и /topup-api/submit в соответствующие публичные Seller routes;
   Cookie и Authorization не пересылаются. Hub наружу не публикуется.
5. Для выбранного аутентифицированного workspace оператор задаёт в Seller
   steam_topup_settings enabled=true, max_amount=100, budget_amount=100; в Hub
   topup_permissions — consumer_id='seller', тот же workspace_id, enabled=true,
   max_amount=100. Это явный допуск к общему балансу поставщика, не SaaS-биллинг.
6. После согласования личного теста включить отдельные глобальные switches Seller
   и Hub. Существующие SUPPLIER_HUB_PURCHASES_ENABLED и INTERHUB_PAY_ENABLED также
   должны разрешать покупки. Запустить compose --profile steam-pilot up -d.
7. Владелец создаёт одну ссылку на 100 ₽ и сам вводит логин/нажимает «Пополнить».
   Проверить реальный результат Steam и конвертацию. Повторное нажатие должно
   показывать тот же итог. Применение миграций само по себе платежей не запускает.

Для остановки новых платежей закрыть topup_permissions в Hub и разрешение пилота
в Seller; оставить обработчики для сверки начатого. Выключение только Seller
не отменяет уже принятую Hub покупку. Общие switches Hub также приостанавливают
его существующий worker целиком; для пилота использовать отдельное DB-разрешение.

## Проверки

- Seller: реальные миграции в disposable seller_test_*, конкурентные клики и
  worker, две рабочие области, повтор создания/активации, lost response после
  фиксации Hub, отмена/истечение/бюджет, запрет смены суммы, HTTP owner-проверка.
- Hub: состояние TOP_UP без кода, неизменяемые реквизиты, timeout и падение после
  payment_started, ограниченный retry check; отдельные PostgreSQL-тесты конкурентного
  enqueue/claim и сохранения pay_started_at. Существующие ваучерные тесты сохраняются.
- Frontend: npm run check в Seller и homtech_info; визуальная проверка 1280/390 px.
- В локальном pgserver нет pgcrypto: только тестовые encryption-функции заменены
  заглушками во временных БД; реальное шифрование этой проверкой не подтверждается.

Локальный `?preview=steam` существует только в DEV, показывает 100 ₽ и не вызывает
API пополнения. Production без token всегда блокирует форму.
