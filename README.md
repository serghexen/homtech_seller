# HomTech Seller

Самостоятельный кабинет продавца для подключения Ozon и Яндекс Маркета.

Постоянные правила multi-tenant разработки и безопасных worker-ов находятся в
[`AGENTS.md`](AGENTS.md). План контролируемого переноса Ozon из CRM — в
[`docs/OZON_CRM_CUTOVER_CHECKLIST.md`](docs/OZON_CRM_CUTOVER_CHECKLIST.md).

Базовые синхронизации маркетплейсов остаются безопасными операциями чтения: Seller получает и хранит локальный снимок подключений, каталога, остатков и заказов. Для цифровой выдачи есть отдельный защищённый контур с независимыми kill switch: по умолчанию он не подготавливает и не отправляет коды.

## Границы продукта

- отдельный репозиторий, VM и PostgreSQL;
- отдельный ключ шифрования токенов маркетплейсов;
- отдельный ключ шифрования ручных пулов;
- собственные пользователи, организации и роли;
- связь с CRM в будущем — только через SSO/API, без общего доступа к базам данных.

Подробнее: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Локальный запуск инфраструктуры

```bash
cp .env.example .env
docker compose up -d postgres
docker compose --profile maintenance run --rm migrate
docker compose up -d api worker web
curl http://127.0.0.1:18080/health
```

PostgreSQL намеренно не публикуется в интернет: он слушает только loopback-порт VM для SSH-туннеля. В production API также будет доступен только через reverse proxy.

Для локального запуска API и Vue с PostgreSQL на VM используйте [docs/LOCAL_DEVELOPMENT.md](docs/LOCAL_DEVELOPMENT.md). База на VM открывается только в SSH-туннеле.

Закрытое соединение production Seller с Supplier Hub и безопасный откат описаны
в [docs/SUPPLIER_HUB_CONNECTION.md](docs/SUPPLIER_HUB_CONNECTION.md).

## Версия

Текущая версия Seller задаётся в `web/package.json`, отображается в правом нижнем углу интерфейса и обновляется при каждом релизе. Версию FastAPI в `api/app.py` меняем одновременно; автоматический тест проверяет, что значения совпадают.

## Авторизация

Seller пока использует самостоятельные email/пароль аккаунты. Первая регистрация создаёт организацию (workspace), владельца, тариф Basic и изолированную область данных. Тарифы и подключения маркетплейсов принадлежат workspace, а не персональному пользователю. Basic поддерживает локальный пул и ручную выдачу; настройка связок и автовыдача через Supplier Hub доступны в Pro. Тариф применяется из PostgreSQL без рестарта Seller.

SSO с CRM будет добавлен позже через `auth_subject`; он заменит способ входа, не перемещая магазины, заказы или подписки.

## Состояние первого этапа

Seller уже содержит самостоятельную авторизацию, подключения Ozon и Яндекс Маркета, локальные снимки каталога, остатков и заказов, настройки карточек и зашифрованные пулы. Оператор может подготовить выдачу из пула, ручного комплекта или сохранённого сообщения поддержки, а затем отдельно подтвердить отправку. Все мутации по умолчанию выключены.

Публичный endpoint `POST /api/marketplaces/yandex/notifications` подготовлен для будущего переключения API-уведомлений Яндекс Маркета. Он проверяет официальные сети Маркета, сохраняет события идемпотентно и отвечает на `PING`. До финального отключения CRM переменная `YANDEX_MARKET_WEBHOOK_PROCESSING_ENABLED=false` оставляет все бизнес-события в состоянии `paused`: Seller не запрашивает заказ и не запускает выдачу.

Для цифровой позиции DBS-заказа (`delivery_type=DIGITAL`) Seller умеет создать локальную fulfillment-запись и атомарно зарезервировать только полный комплект ключей без их расшифровки. Физические позиции не получают такую запись и не показывают действие подготовки. Автоматический резерв закрыт глобальным выключателем `SELLER_POOL_RESERVATION_ENABLED=false`, а также выключателями магазина и товара. Supplier Hub находится перед локальным пулом в resolver и дополнительно требует Pro, полной связки карточки и собственных защитных переключателей.

Оператор или владелец может открыть цифровой заказ Яндекс Маркета или Ozon в статусе «В процессе», явно подготовить локальную выдачу и отдельным подтверждением поставить готовый комплект в долговечную очередь отправки. Обычные списки и API подготовки возвращают только маскированные данные; worker расшифровывает комплект в памяти непосредственно перед запросом маркетплейсу. Для проверки уже закреплённого или выданного кода есть отдельное точечное действие: оно проверяет workspace, роль и точную позицию заказа, после чего раскрывает только выбранный комплект. Пока worker не взял задание, постановку можно отменить; после начала сетевого запроса автоматический откат запрещён.

В карточке товара настройки выдачи собраны в одну видимую цепочку: Supplier Hub, список ключей, сообщение поддержки и ручной ввод. Можно сохранять включение пула и поддержки, управлять ключами и шаблоном сообщения; это не включает общие kill switch само по себе. В Pro также можно настроить связку Supplier Hub, а в Basic этот блок остаётся видимым, но заблокированным без удаления сохранённых данных.

На установленном стенде ручные изменения дополнительно закрыты `SELLER_MANUAL_FULFILLMENT_ENABLED=false`. Внешняя отправка имеет два независимых разрешения: глобальный `SELLER_YANDEX_OUTBOUND_ENABLED` или `SELLER_OZON_OUTBOUND_ENABLED` и `fulfillment_outbound_enabled` у конкретного магазина. Все значения по умолчанию безопасны: применение миграции само по себе ничего не отправляет.

Ozon не присылает Seller события о цифровых отправлениях. Worker читает `/v2/posting/digital/list` по расписанию, которое хранится у подключения в БД и меняется из интерфейса без рестарта. Polling только обновляет локальный снимок и fulfillment-состояние; он не передаёт коды. Передача цифрового комплекта использует отдельную очередь и `/v1/posting/digital/codes/upload`. Таймаут после начала запроса переводит выдачу в `unknown` и запрещает слепой повтор до ручной сверки.

Worker фиксирует состояние `sending` до HTTP-запроса. Успех переводит выдачу в `submitted`, а подтверждение заказа webhook-ом или периодической сверкой — в `delivered` и окончательно расходует ключи. Однозначный `4xx` возвращает комплект в резерв. Таймаут, сетевой сбой или `5xx` переводит выдачу в `unknown` без автоматического повтора, чтобы исключить двойную доставку.

Telegram-уведомления о ручной выдаче принадлежат Seller и работают отдельным контейнером `notifier`. Переход fulfillment в `manual_required`, `unknown`, ошибку или отмену транзакционно создаёт событие в БД; сетевой вызов Telegram выполняется позже и не блокирует API или worker. Получатели изолированы по workspace, а каждая доставка имеет уникальную запись, lease и долговечный retry с backoff. Бот выключен общим `SELLER_TELEGRAM_NOTIFICATIONS_ENABLED=false` до контролируемого переноса получателей из CRM.

После подтверждённой маркетплейсом отправки цифрового комплекта отдельная долговечная очередь повторно публикует целевой остаток карточки. Эту же очередь использует явная команда «Опубликовать» в блоке остатка: оператор сначала сохраняет значение в Seller, подтверждает отправку и видит её фактический статус. Для Яндекса без дневного лимита отправляется «Заданный остаток», с лимитом — меньшее из заданного остатка и оставшейся дневной квоты. Ozon получает сохранённый целевой цифровой остаток через `/v1/product/digital/stocks/import` с задержкой после принятия кодов. Публикация требует соответствующего глобального разрешения (`SELLER_YANDEX_STOCK_OUTBOUND_ENABLED` или `SELLER_OZON_STOCK_OUTBOUND_ENABLED`) и `stock_outbound_enabled=true` у магазина; по умолчанию оба пути выключены. Входящий текст инструкции нормализуется: legacy-последовательности `\\n` перед отправкой становятся настоящими переносами строк.

После контролируемого включения глобального и магазинного kill switch тот же worker арендует событие, повторно проверяя актуальный флаг магазина, запрашивает у Яндекса только указанный `orderId` и обновляет локальный снимок существующим idempotent-upsert. Полная история не перечитывается, watermark ручной синхронизации не продвигается. Обычная синхронизация заказов использует тот же механизм сверки fulfillment, поэтому пропущенный webhook не оставляет локальный резерв у отменённого или завершённого заказа. Ошибки повторяются с backoff, истёкший lease восстанавливается после падения процесса, а исчерпавшее попытки событие переходит в `dead`. Выдача и InterHub к этому обработчику не подключены.
